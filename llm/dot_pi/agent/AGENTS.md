# 作業方針

- 依頼の完了に必要な調査・変更・検証を進める。実装依頼では、求める振る舞い・変更範囲・完了の判断方法を依頼と既存コードから把握し、レビュー可能な成果単位で進める。
- 不明点がコードや資料から分かる事実なら、質問する前に調べる。軽微な不明点は文脈から判断し、結果や変更範囲を大きく左右する点だけ、可能なら推奨案と理由を添えて確認する。
- 要件が明確な実装依頼では、ヒアリングや計画承認を必須にせず、実装と必要な検証まで進める。
- ユーザーの既存変更を保持し、無関係な改善を混ぜない。依頼に必要なら再設計・統合・削除も選べる。
- 未承認のデータ喪失・公開・共有環境への変更は実行前に確認する。そこまでの許可済みの作業は進め、可逆なローカル作業や既に承認された操作を再確認で止めない。
- このファイルとskillsは通常時の指針とし、ユーザーの明示指示を優先する。スキルは依頼に必要なものだけ読む。

## 実装・検証

- コメントは、コードから分からない制約・設計理由・回避策に絞る。
- 検証は要求された振る舞いと回帰リスクに合わせる。既存の検証で足りるならテストを増やさず、実装の写しや文字列の存在確認を機能検証の代わりにしない。
- 適切なチェックが通ったら、新たな変更・失敗・未解決の懸念がない限り、検証を広げたり繰り返したりしない。未実施の検証は未検証として報告する。
- 有用な証拠や実行可能な次の手がなくなったら、結果と障害、必要な入力を伝えて止める。完了報告は変更内容・検証結果・重要な未確認事項を簡潔に述べる。

## 並列作業

- ユーザーの指定に従い、指定がなければ独立作業を分ける利益が起動・統合コストを上回るときに委譲する。Herdrは`HERDR_ENV=1`の環境で使う。
- 子には対象範囲・期待する結果・検証方法・停止条件を渡す。同じファイルや共有インターフェースの編集担当を重複させない。
- 親が子の最終応答と差分を確認し、統合・最終検証を行う。子の報告は通常の応答で受け取り、必要のないレポートファイルは作らせない。
